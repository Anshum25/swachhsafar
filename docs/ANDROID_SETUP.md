# Swachh Safar Android app (Capacitor)

The Android app and the PWA are one codebase. `src/` is built once by Vite; the PWA is served by nginx
and the same `dist/` is packaged inside the APK by Capacitor, which adds what a browser cannot do — today
the Developer-options block, later a USB fingerprint scanner.

The project in `android/` is generated by `npx cap add android` (Capacitor 8) and then committed. Only four
things in it are ours: the two Kotlin files, the app's Gradle configuration, the manifest permissions and
the Proguard rules. Everything else is the Capacitor template and may be regenerated.

## 1. Directory structure

```
android/
├── gradlew, gradlew.bat, gradle/wrapper/   committed, so CI needs no Gradle installation
├── build.gradle            AGP + Kotlin plugin
├── variables.gradle        SDK levels and dependency versions
├── settings.gradle         + capacitor.settings.gradle (generated by `cap sync`)
└── app/
    ├── build.gradle        versionCode/versionName, release build type, plugin dependencies
    ├── proguard-rules.pro  keeps the Capacitor plugin classes R8 would otherwise strip
    └── src/main/
        ├── AndroidManifest.xml
        └── java/in/itfarmer/swachhsafar/
            ├── MainActivity.kt                  registers the plugin
            └── security/SwachhSecurityPlugin.kt
```

Not committed, recreated by `npx cap sync android` on every build: `app/src/main/assets/public` (the web
build), `app/src/main/assets/capacitor.config.json`, `app/src/main/res/xml/config.xml` and
`capacitor-cordova-android-plugins/`.

> Kotlin reserves `in`, so both files declare ``package `in`.itfarmer.swachhsafar`` with backticks. Written
> plainly it is a syntax error — the reason the earlier hand-written project had never compiled.

## 2. Native capabilities (Kotlin)

`SwachhSecurityPlugin.kt` implements the bridge contract used by `src/security/native.js`:

| Method | Implementation |
|---|---|
| `getDeviceIntegrity` | `Settings.Global.DEVELOPMENT_SETTINGS_ENABLED` and `ADB_ENABLED`. The app refuses to open while Developer options are on (`src/security/DeveloperModeGate.jsx`) |
| `openDeveloperSettings` | `Settings.ACTION_APPLICATION_DEVELOPMENT_SETTINGS`, falling back to the settings root |
| `getLocationStatus` | `ACCESS_FINE_LOCATION` and `LocationManager.GPS_PROVIDER` |
| `requestLocationPermission` | Runtime location permission through Capacitor's permission aliases |
| `getCurrentLocation` | `FusedLocationProviderClient` at `PRIORITY_HIGH_ACCURACY`, with mock detection (`loc.isMock` / `isFromMockProvider`) |
| `openLocationSettings` | `Settings.ACTION_LOCATION_SOURCE_SETTINGS` |
| `getNetworkState`, `networkChange` | `NetworkCapabilities` (connected, VPN, transports) and a `ConnectivityManager.NetworkCallback` |
| `secureGet` / `secureSet` | `EncryptedSharedPreferences` backed by the Android Keystore (`MasterKey`, AES256-GCM) |
| `getMonotonicTime` | `SystemClock.elapsedRealtime()` / `uptimeMillis()` for tamper detection |
| `appResume` event | Emitted from `handleOnResume`, so the Developer-options check runs again on every resume |

Permissions in the manifest: `INTERNET`, `ACCESS_NETWORK_STATE`, `ACCESS_FINE_LOCATION` and
`ACCESS_COARSE_LOCATION` for the plugin; `CAMERA` and `RECORD_AUDIO` because the WebView asks for them on
the app's behalf (face verification and voice notes). `allowBackup` is off: records never leave the device
through an automatic backup.

## 3. What differs inside the APK

The WebView serves the app from **`https://localhost`**, not from the site, so:

- **API calls.** The APK build sets `VITE_API_BASE_URL=https://ehk.itfarmer.in/api/v1`; the PWA keeps the
  relative default. `src/services/serverOrigin.js` derives the server's origin from it, and everything that
  must reach the server (media links, `/downloads/...`) goes through `serverUrl()`. The PWA's URLs are
  unchanged, because there `serverUrl()` returns the path as it is.
- **CORS.** `https://localhost` must be in the backend's `CORS_ORIGINS`, and nginx must send
  `Access-Control-Allow-Origin` for `/downloads/latest.json`. See `docs/DEPLOYMENT.md`.
- **No service worker.** The build is already packaged in the APK, so `registerServiceWorker()` does
  nothing there, and the PWA install banners are hidden.
- **Updates** are a new APK, not a new service worker: `src/pwa/appUpdate.js` compares the commit the build
  was made from (`VITE_BUILD_SHA`) with `sha` in `/downloads/latest.json` and offers the download.
- `/models/face/*` stay relative on purpose: those files are bundled in the APK.

## 4. Building

Prerequisites: **JDK 21** (Capacitor 8 compiles against Java 21), Android SDK platform 36 and build-tools,
Node 20+.

```bash
npm ci
npx vite build && npx cap sync android     # the web build must exist before Gradle runs
cd android && ./gradlew assembleRelease
```

### The version number

`versionName` and `versionCode` are not written in `android/app/build.gradle`: it reads `package.json`.
Raise the version there, nowhere else.

`versionCode` is that version plus the CI run number — `2.0.3` on run 418 is `20003418`. Android refuses
to install an APK whose `versionCode` has not risen above the installed one, and several releases a day
share a version name, so the run number is what makes each release installable over the last. A version
bump raises the base by at least 1000, so the code rises across a bump as well as within one. A local
build has no run number and gets `…000`, which is fine for a build nobody publishes.

`deploy/scripts/receive-release.sh` refuses an APK whose `versionCode` has not risen above the published
one, as `publish-apk.sh` already did: such an APK downloads, fails to install, and leaves the phone
offering the same update for ever.

Output: `android/app/build/outputs/apk/release/app-release-unsigned.apk`. Release builds are minified,
resource-shrunk and not debuggable, and Gradle holds **no** signing configuration: signing happens outside
Gradle so no key material is ever in the repository.

Sign it the way CI does (`.github/workflows/deploy.yml`):

```bash
zipalign -f 4 app-release-unsigned.apk aligned.apk
apksigner sign --ks release.jks --ks-key-alias swachh-safar --out app.apk aligned.apk
apksigner verify --print-certs app.apk
```

### Releases

CI builds and signs the APK when the repository variable `BUILD_APK` is `true`, describes it with
`scripts/describe-apk.py`, and sends it with the web bundle to the server, where
`deploy/scripts/receive-release.sh` publishes `swachh-safar-<sha>.apk`, `swachh-safar-latest.apk` and
`latest.json`. `deploy/scripts/publish-apk.sh` does the same by hand from a locally built APK.

The signing key is generated locally, never committed, and kept in two backups: **if it is lost, no
installed app can ever be updated again** — Android refuses an update signed with a different certificate.

## Publishing the APK for download (2026-11-06)

**Why the download was browser-dependent:** no APK had ever been published. nginx answered `/downloads/swachh-safar.apk` with the app's `index.html` (200, text/html). Chrome, because of the link's `download` attribute, saved that HTML as a ".apk"; other browsers (and the service worker, which served the app shell to every navigation) simply showed the app. Fixed: nginx serves `/downloads/` from `/var/www/html/swachhsafar2.0/downloads/` with `application/vnd.android.package-archive` + `Content-Disposition: attachment` and a real 404 when missing; the service worker no longer handles `/downloads/`; the public page `/download` uses a plain link and reads `latest.json`.

Steps (on a machine with JDK 21 + Android SDK, see above):
1. `npm run build && npx cap sync android`, then in `android/`: `./gradlew assembleRelease`, and sign the output as shown above (the keystore is never committed; keep an offline backup — losing it means installed apps can never be updated).
2. Copy the signed APK to the server and run `sudo deploy/scripts/publish-apk.sh app.apk`. It verifies the signature (refuses debug keys/builds and a changed certificate), the package `in.itfarmer.swachhsafar`, that versionCode increased, then publishes `swachh-safar-<version>.apk`, `swachh-safar-latest.apk` and `latest.json` (size, SHA-256, certificate digest, date).
3. Install the nginx change once: `sudo cp deploy/nginx/swachhsafar-app.conf /etc/swachhsafar/nginx/app.conf && sudo nginx -t && sudo systemctl reload nginx`.
4. Check: `curl -sI https://ehk.itfarmer.in/downloads/swachh-safar-latest.apk` → 200, `application/vnd.android.package-archive`, `Content-Disposition: attachment`.
